# Wiki schema

This wiki is an LLM-maintained knowledge base about PLDAPS_vK2 (the "LLM Wiki" pattern).
Claude writes and maintains it; people read it. The **raw sources** are the repository
itself (code, existing `.md` docs, git history) plus facts the user states in conversation.
The wiki never modifies raw sources.

`CLAUDE.md` holds the short must-follow rules (strobe codes, postFlip, quintet). The wiki
holds the depth and **links** to CLAUDE.md rather than restating its rules.

## Layout

| Path | Contents |
|---|---|
| `index.md` | GENERATED catalog of every page. Never hand-edit; run `wiki_gen.py index`. |
| `log.md` | Append-only, one line per entry: `- [YYYY-MM-DD] <op> \| <title> — <note>` where op ∈ bootstrap, update, ingest, query, lint. `grep "^- \[" wiki/log.md \| tail -5` shows recent activity. |
| `overview.md`, `gotchas.md`, `timeline.md`, `docs-catalog.md` | Start-here synthesis, traps, history, catalog of existing repo docs. |
| `open-issues.md` | The one place suspected bugs and stale docs are recorded: ID, where, what happens, effect on recorded data (since which commit), confidence. Resolved items move to its "Resolved" section with the fixing commit. |
| `concepts/` | Cross-cutting mechanisms (quintet, `p`, strobing, postFlip, …). |
| `library/` | `+pds` by functional area, `+pdsActions`, rig configs, GUI. |
| `tasks/` | Family pages (`family-*.md`) and one page per `tasks/*` directory. |
| `reference/strobe-codes.md` | GENERATED strobe registry; run `wiki_gen.py strobes`. |
| `analyses/` | Answers to questions worth keeping, filed back from conversations. |
| `_tools/` | `wiki_gen.py`, `wiki_lint.py`, `wiki_lib.py` (Python 3 stdlib). |

## Page format

```yaml
---
title: gSac_4factors
type: task                # task | family | concept | library | reference | catalog | analysis | meta
category: Tasks — gSac family   # index heading; prefixes: Start here, Concepts, Library, Reference, Tasks, Catalogs, Analyses
summary: One line shown in index.md
status: active            # task/family pages only: active | legacy | wip
task_dir: tasks/gSac_4factors/   # task pages only; enables the generated facts block
sources:                  # files (preferred) or dirs (trailing /) this page describes
  - tasks/gSac_4factors/gSac_4factors_run.m @ 1a2b3c4d5e
verified_at: e48934be     # informational: HEAD when last stamped
updated: 2026-10-15
---
```

- `@ <hash>` is written by `wiki_gen.py stamp`; never type hashes by hand. A page is
  **stale** when any listed source's content hash changes (works for uncommitted edits and
  edits made outside Claude). List the specific files a page describes; a directory source
  goes stale on any change inside it.
- Links: relative markdown links (`[strobe codes](../concepts/strobe-codes.md)`). Refer to code
  by repo path and function name, never line numbers.
- Task pages keep the `<!-- GEN:facts:start -->…<!-- GEN:facts:end -->` block (files, states,
  strobeList) generated by `wiki_gen.py facts`; write narrative around it, never inside it.

### Task page sections
1. One-paragraph purpose (what the subject does; what the experiment measures).
2. Trial flow (state sequence in words, linked to the generated state list).
3. Conditions / trial structure (how `_next` / `initTrialStructure` pick trials).
4. Key trVars and settings variants (what differs between settings files).
5. Data & strobes: what is saved, notable strobes, link to the data dictionary.
6. **Session practice & decisions**: facts not recoverable from code (how the user actually
   runs it, why choices were made). Only what the user stated or a doc records; cite it.
7. **Data/strobe change history** (active tasks): `date — commit — change to saved data or strobes`.
8. Related: family page, concepts, docs.

## Writing rules

- **Grounded:** every factual claim must be checkable in a cited source. If you cannot
  confirm a claim, delete it — do not hedge it.
- **Neutral:** describe what the code does and why. Do not present deliberate design choices
  as problems or suggest fixes. Suspected genuine bugs (e.g. strobe-code collisions) are
  verified, mentioned to the user, and recorded only on `open-issues.md` (neutral wording);
  other pages may link to an issue by ID (`[S1](../open-issues.md#s1-…)`) but don't restate it.
- **Compact:** summarize and link to data dictionaries / planning docs instead of copying them.
- **One owner per topic:** put a fact on the most specific page and link to it from others.

## Workflows

### update (after code changes; the Stop hook asks for this)
1. For each changed source file, find pages citing it (`sources:`) — the hook lists them.
2. Read the diff (`git diff <file>` or the edit you just made) and revise the narrative of
   those pages. Add a "Data/strobe change history" line when saved data or strobes changed.
   Record any rationale or session practice the user stated in this conversation.
3. If a change creates something with no page (new task, new +pds area), create one.
   If it fixes an item on `open-issues.md`, move that item to "Resolved" with date + commit
   (or "uncommitted"); if it introduces a suspected bug, verify it and add an item.
4. Run `python3 wiki/_tools/wiki_gen.py all` then `python3 wiki/_tools/wiki_gen.py stamp <pages you verified>`.
5. Append one line to `log.md`.
6. If nothing documented changed (formatting, comments, analysis scripts), make no edits.

### stale pages (reported at session start)
`python3 wiki/_tools/wiki_gen.py stale` lists pages whose sources changed (often edits made
in MATLAB, outside Claude). For each: diff the sources since the page's `verified_at`
(`git diff <verified_at> -- <path>`), update, stamp, log.

### ingest (a new doc, paper, design note, or user explanation)
Read it, add it to `docs-catalog.md` (if it is a repo file), fold its facts into the relevant
pages (citing it), stamp, log.

### query
Read `index.md`, then the relevant pages; answer with links to pages and source files. If the
answer is a reusable synthesis (comparison, analysis, how-to), offer to file it as
`analyses/<slug>.md` (type: analysis) and log it.

### lint
`python3 wiki/_tools/wiki_lint.py` for mechanical problems; then read pages for contradictions,
claims superseded by newer code, concepts mentioned but lacking a page, and missing links.
Fix, stamp, log.
