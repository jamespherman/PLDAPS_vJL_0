# SRS_mooving

SRS_mooving is the [SRS_Task_Smooth](SRS_Task_Smooth.md) salience-vs-reward choice task with
target positions that change every trial. Reward still belongs to target identity (T1
horizontal, T2 vertical rectangle) in unsignaled blocks, and salience, timing, reward
sampling, correction trials and display modes are all inherited unchanged. Only the geometry
differs: T1 and T2 no longer occupy two fixed left/right positions, so a choice of identity
cannot be confused with a choice of screen location. The directory name keeps its original
spelling ("mooving"); the task name is `srsMoving`.

**Dependency.** `srsMoving_settings.m` adds `tasks/SRS_Task_Smooth/`, its `supportFunctions/`
and its `actions/` to the end of the MATLAB path (this task's own folders go first, so its
overrides win), then calls `srsSmooth_settings` and points `p.init.taskFiles` at the
`srsMoving_*` wrappers. It errors if the sibling SRS_Task_Smooth folder is missing.

## Trial flow

The same as SRS_Task_Smooth. `srsMoving_run` calls `srsSmooth_run` unchanged, then adds spatial
descriptors of the completed choice (`chosenPhysicalSide`, `chosenVerticalSide`,
`chosenHorizontalRank`, `chosenVerticalRank`, chosen target angle and X/Y).

## Conditions / trial structure

Block schedule, reward and salience come from SRS_Task_Smooth's `nextParams`. After it runs,
`srsMoving_next` calls `assignDubeyMovingLocations`, which on a normal trial:

- draws the T1 angle uniformly on [0°, 360°);
- draws a separation uniformly in [`movingTargetMinSeparationDeg`, 180°] (default 90°) in a
  random direction to place T2;
- puts both targets at `movingTargetEccDeg` (default 10°) from fixation.

A forced correction repeat restores the exact geometry from the correction snapshot instead of
resampling. The schedule's `T1Side`/`T2Side` values become balancing slots only. Absolute
hemifields (`T1PhysicalSide`, `T2PhysicalSide`: 0 meridian, 1 right, 2 left; vertical
equivalents 1 upper, 2 lower) and relative ranks (`rightmostTargetID`, `uppermostTargetID`, …)
are computed from the actual coordinates. The README explains why "right hemifield" and
"rightmost target" are kept separate.

This task's `updateTrialsList` triggers a left/right correction only when the targets fall on
opposite sides of the vertical meridian (`movingTargetsStraddleLR`), using the chosen
physical side.

## Data & strobes

`p.trData` gains the trial geometry (`movingT1AngleDeg`, `movingT2AngleDeg`,
`movingAngularSeparationDeg`, `T1_locDegX/Y`, `T2_locDegX/Y`, physical/vertical sides, ranks,
straddle flags, `highRewardPhysicalSide`, `highSaliencePhysicalSide`) and the chosen-target
descriptors.

Strobes:

- `srsMoving_init` sets `p.init.taskCode` to `uniqueTaskCode_SRS_mooving` (32024) and stops
  with an error if any strobeList name, or any of the moving codes, is missing from
  `+pds/initCodes.m`.
- The settings file appends 11 rows (codes 20054–20064: target angles ×10, separation ×10,
  eccentricity ×100, physical sides, chosen physical side, straddle flags, chosen ranks) to the
  inherited SRS strobeList.
- It redirects the inherited spatial rows to the real geometry: `T1Side`, `T2Side`,
  `highRewardLocation`, `highSalienceLocation` and `chosenTarget` are strobed from the
  `*PhysicalSide` fields.
- `srsMoving_finish` replaces the NaN placeholders of the inactive salience mode with 0, checks
  that every strobeList value is a finite integer in [0, 32767], then calls `srsSmooth_finish`.
  It accepts `salienceType` 1 (hue) and 2 (luminance) only.

The generated facts block lists no strobeList because the list is built by appending to the
inherited one. See the SRS_Task_Smooth page for the base list.

`Simple_analysis/` (`RUN_SIMPLE_MOVING_ANALYSIS.m`) compares identity/value strategies with
spatial strategies; see the README.
