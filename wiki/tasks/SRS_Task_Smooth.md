# SRS_Task_Smooth

SRS (Salience–Reward–Saccade) asks what a monkey chooses when salience and reward disagree.
On each trial the subject fixates, one or two rectangular targets appear while fixation is held,
the fixation point goes off, and the subject saccades to a target and holds it. **T1** is a
horizontal rectangle and **T2** a vertical one (2° × 0.667°). Reward belongs to target
**identity**: within an unsignaled block one identity is "rich" and the other "poor". Salience
is set per trial, independently of identity, by how strongly a target differs from the
background. Congruent trials put high salience and high reward on the same target; conflict
trials put them on opposite targets. The design follows Dubey et al. 2023 (Neuron 111:3321),
which the code cites for the reward ranges and the log-uniform sampling.

The quintet files are named `srsSmooth_*` (`p.init.taskName = 'srsSmooth'`). The settings
file's header comment still describes the "scd" task it was copied from.

## Trial flow

`trialBegun` → `showFix` (acquire within `fixWaitDur`, 0.3 s) → `dontMove` (hold
`fixDurReq`, uniform 0.5–0.8 s) → `targetDelay` (targets on, fixation still on, for
`targetDelayDurationMs`) → `MakeSaccade` (fixation off = go; saccade within `responseWindow`,
0.45 s) → `checkLanding` → `holdTarg` (`targHoldDuration`, 0.2–0.3 s) → `sacComplete` (tone,
reward, then `postRewardDuration`). Failures end in `nonStart`, `fixBreak`, `noResponse` or
`inaccurate`, and `p.trData.failureReason` records the specific cause (for example
`"fixbreakduringdelay"`, `"blinkDuringSaccade"`, `"targetHoldBreak"`). Saccade onset uses an
online velocity threshold (`eyeVelThresh`, 100 °/s). The joystick is read but no state
requires it, and the states inherited from change detection (`holdJoy`, `hit`, `cr`, …) are
defined but never entered. `fixOn`, `targetOn` and `fixOff` are timestamped through the postFlip
mechanism ([drawing and postFlip](../concepts/drawing-and-postflip.md)); `targetDelay` waits for
`timing.targetOn > 0` before timing the delay.

On a successful trial the reward is chosen by the identity the subject picked
(`rewardDurationT1` or `rewardDurationT2`) and recorded in `p.trData.deliveredRewardDurationMs`.

## Conditions / trial structure

`initTrialStructure` only defines the column layout. A new schedule is built at the start of
every block (`nextParams` → `startNewBlock` → `buildSrsBlockSchedule`):

- **Block reward.** The first block's rich identity is `randi(2)`; after that it alternates
  (`CurrentBlockType = 3 - CurrentBlockType`). `chooseBlockReward` draws two block means
  uniformly from [`blockMeanRewardMinMs`, `blockMeanRewardMaxMs`] = [37, 191] ms, at least
  `blockMeanRewardMinSepMs` (40 ms) apart, and multiplies both by `rewardScale` (default 1.5).
  Each trial, `sampleTrialRewards` draws a rich and a poor sample as
  `round(mean + SD·randn)`, where SD = `RewardSdGaussianNoiseMs` (14 ms) × the same scale,
  floored at 1 ms and capped at `maxSingleRewardMs` (400 ms). All of these parameters are
  clamped to safe ranges rather than rejected with an error. `rewardScale` takes effect at the
  next block; `maxSingleRewardMs` takes effect on the next trial.
- **Schedule rows.** Choice rows number `4·randi([ceil(min/4), floor(max/4)])` from
  `minTrialsPerBlock`/`maxTrialsPerBlock` (60–100 by default), split evenly over
  {congruent, conflict} × {T1 right, T1 left}. When `useSingleStimTraining` is on, phase-1
  instruction rows (`nSingleT1PerBlock` T1-only + `nSingleT2PerBlock` T2-only, sides balanced)
  come first. `chooseScheduledRow` samples only from the lowest remaining phase, so no choice
  trial occurs until every instruction row has succeeded.
- **Repeats.** `updateTrialsList` removes a row only after a successful trial; failed rows stay
  eligible. A new block starts when no rows remain. `TotalBlocksTarget` (8) only drives the
  `RemainingBlock` display.
- **Salience assignment.** On congruent trials the high-salience side equals the high-reward
  side; on conflict trials it is the opposite side. On instruction trials
  `highSalienceTargetID = randi(2)`, independent of which target is shown.
- **Correction trials** (optional, off by default). Controlled live from a separate MATLAB window
  (`initCorrectionControlWindow` / `readCorrectionControlWindow`), read before every trial. After a
  successful conflict trial where the subject chose the low-reward target (right-side choices
  only, or both sides if `correctionBothSides`), the same row is forced again with the exact
  stochastic condition restored from a snapshot (`captureCorrectionTrialSnapshot` /
  `restoreCorrectionTrialSnapshot`). This continues until a high-reward choice or
  `correctionTrialMaxRepetition` (15). A correction never carries into a new block. With
  `correctionReduceRightReward`, a right-triggered correction also scales down the right reward.

## Salience modes and settings variants

`salienceType` selects the salience mode and is resolved before the display opens in
`srsSmooth_init`:

| `salienceType` | Display | Salience |
|---|---|---|
| 1 (default) | L48 dual CLUT | DKL hue contrast; background hue 0° or 180° (`backgroundHueIdx = randi(2)`), DKL luminance −0.495, saturation 0.4 |
| 2 | L48 dual CLUT | red DKL luminance ramp, calibrated against `SRS_red_luminance_calibration_20260716.csv` |
| 3 | C24 RGB passthrough (`initDataPixxC24`) | direct-RGB red family 15 from `SRS_direct_rgb_red_family15_20260728.csv`; experimenter overlays go to a separate MATLAB preview window |

In hue mode, `hueSamplingMode` chooses between **smooth** (each target hue = background +
offset, offsets in [10°, 180°] with the pair mean fixed at 95°, drawn by
`chooseContinuousHuePair` and written into reserved CLUT slots 250/251 each trial) and
**classic** (fixed hues: high salience 180° from background, low salience 20°, CLUT 20–23).

|---|---|---|---|
| `srsSmooth_settings.m` | hue, smooth | none | base file |
| `srsSmooth_classic_settings.m` | hue, classic | none | |
| `srsSmooth_training_settings.m` | hue, smooth | 10 T1 + 10 T2 | |
| `srsSmooth_classic_training_settings.m` | hue, classic | 10 T1 + 10 T2 | |

| `srsSmooth_direct_rgb_settings.m` | direct RGB (3) | none | |

With `useThreeOutcomeTones` (the two Moretraining files), `initSrsFeedbackAudio` loads 900 Hz
(rich identity chosen), 450 Hz (poor identity chosen) and 150 Hz (failure) tones; otherwise the
standard high/low tones play. Each variant writes to its own `sessionId` suffix.

`delay_ms_min`/`delay_ms_max` (300–600 ms) are defined in the settings files, and
`sampleTargetDelayMs` exists in supportFunctions, but the `targetDelay` state uses
`targetDelayDurationMs` (450 ms), which `nextParams` does not resample.

GUI quick-access variables (`p.rig.guiVars`) include `salienceType`, `rewardScale`,
`maxSingleRewardMs`, `responseWindow` and the T1/T2 location fields. Changing
`T1_locDegX/Y` and `T2_locDegX/Y` changes the two physical locations; identity-to-side
randomization swaps whole [X, Y] pairs.

## Data & strobes

Sides use `1 = right, 2 = left`; identities use `1 = T1, 2 = T2`. Per trial,
`p.trData` holds the schedule metadata (`nStim`, `singleTargetID`, `T1Side`, `T2Side`,
`schedulePhase`), the choice (`chosenTargetID`, `chosenSide`, `choseHighSalience`,
`outcomeCode`), `failureReason`, `feedbackTone`, `deliveredRewardDurationMs`, the correction
fields, and `timing.*` (seconds from `trialStartPTB`, `-1` if the event did not occur).
`p.status` holds block and reward state (`CurrentBlockType`, `highRewardTargetID`,
`highSalienceTargetID`, `ActualRichReward`, `ActualPoorReward`, `BlockRewardScale`,
`BlockRewardSdMs`). `outcomeCode` describes the **salience** choice (1 high, 2 low; 10/11 for
T1-only/T2-only instruction trials); whether the rich target was chosen comes from comparing
`chosenTargetID` with `highRewardTargetID`. `pds.saveP` also zips the task folder into the
session folder on trial 1 and does not save non-start trials ([data saving](../concepts/data-saving.md)).

Event codes come from the state machine and `playTone`. With three-tone feedback, `highTone`
(9003) marks a rich-identity choice and `noiseTone` (9002) a poor-identity choice, so the
reward choice can be read from the digital stream directly. The per-trial parameter
`strobeList` (generated table above) is passed to `pds.strobeTrialData` in `srsSmooth_finish`.
Its first row is `taskCode`, and `srsSmooth_settings.m` does not assign `p.init.taskCode`;
because `pds.strobeTrialData` wraps the whole loop in one `try`/`catch`, the data dictionary
records that none of the strobeList values reach the digital stream in this task, so trial
conditions come from the saved trial files. The data dictionary explains how to confirm this per
session from `p.trData.strobed` and how to align trials to Ripple recordings.

Full field-by-field reference: [srsClassic_Moretraining data dictionary](../../data_dictionaries/srsClassic_Moretraining_data_dictionary.md)
(written for the classic Moretraining variant; the other variants share all fields).

## Actions and analysis folders

`actions/` holds i1Pro photometer tools used to build the luminance calibrations
(`i1LivePhotometer` runs in a second MATLAB process, `i1MeasureSrsRedLumRamp`,
`i1ScanDklRedLumAxis`, `i1ScanRedRgbDkl`, `i1ScanRedRgbDirect`, `i1FindGrayBackgroundLum`,
plus `i1CalibrateAndMeasure`, `i1Validate`, `dklToRgbFileMaker`). Some of them are started by
setting a `trVars` flag and pressing Run; `srsSmooth_run` then measures and returns, and
`srsSmooth_finish` skips the normal trial pipeline.

Offline analysis lives in `SRS_behavior_analysis_2/` (standalone loader `srs_load_session`,
statistics, figures and per-session reports; see its README) and `Simple_analysis/` (a one-page
strategy summary; see its README). Both folders also hold committed per-session outputs.
`SELF_TEST_SRS_MORETRAINING_LOGIC.m` runs hardware-free checks of the correction reward
reduction, the delay sampler, strobeList code names and the reward-delivery guard.

## Session practice & decisions

- The 2026-08-19 classic-Moretraining session ran before `rewardScale` existed; the data
  dictionary records that its behavior equals `rewardScale = 1` and that the 2026-08-20 session
  used 1.5.
- `rewardScale` was introduced because the published 37–191 ms range paid too little to keep
  the animal working (sessions earned about 31–50 ml); scaling both means rather than re-centering
  keeps rich and poor values overlapping across blocks (commit da18cf11).
- The trial SD scales with `rewardScale` so that rich/poor discriminability matches the paper
  and block transitions stay as hard to detect (commit c79754eb).
